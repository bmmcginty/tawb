tweb as an edbrowse backend
===========================

A discussion of how to hand live pages from a real browser to edbrowse and
let edbrowse render, navigate and fill them out, written after reading the
edbrowse source in edbrowse/src and the plugin in edbrowse/plugins.

Everything asserted about edbrowse below was checked against that source,
with file and line references so it can be re-checked when edbrowse changes.

Short version: the protocol-plugin idea works for reading, and cannot work
for forms. edbrowse refuses to submit a form to any protocol other than
http, https, gopher, gophers and mailto (src/html.c:3081-3095, message
"cannot submit using protocol %s"). The way out is small and keeps the
plugin: serve the pages from a loopback HTTP origin and let the entry-point
plugin hand back a document carrying <base href="http://127.0.0.1:PORT/...">,
which edbrowse honours (src/html-tags.c:1541). From that point every link
and every form action is an ordinary http URL, and all of edbrowse's
machinery — g, i=, i*, ib, A, rf, ^ — works with no special cases.


1. What the existing plugin does, and why we need something else
---------------------------------------------------------------

edbrowse/plugins/config/render-chrome.rc declares:

    plugin {
        type = */*
        desc = Render page with Chrome
        protocol = chrmrndr
        program = edbrowse-plugin-chrome %i
        outtype = h
    }

and edbrowse/plugins/scripts/edbrowse-plugin-chrome is 40 lines of Python
that starts headless Chrome through selenium, polls driver.page_source until
it stops changing, and writes the HTML to stdout.

It is exactly the right shape and exactly the wrong browser. Three problems,
in increasing order of importance:

  - It is headless and selenium-launched, which is the automated browser this
    project exists not to use. Cloudflare's check on pastebin.com never
    clears under it. Any tweb version of this plugin must attach to the
    ordinary browser tweb already drives, not start one of its own.

  - It is one-shot. The page is rendered once and handed over dead: no click
    reaches the live DOM afterwards, so anything that happens after load —
    a play button, a menu, a form that posts by script — is unreachable.

  - It renders whatever the page looks like at that instant with no identity
    for anything in it. There is no way to say "activate that element".

What we want is the same entry point with a live session behind it, which is
what the tab-element ids are for.


2. How edbrowse's plugin machinery actually works
-------------------------------------------------

Measured, not remembered:

  - A plugin matches by protocol, suffix, content type or urlmatch
    (src/isup.c:3054 findMimeByURL; protocol is tried first unless sxfirst).

  - For a protocol match, edbrowse never fetches anything itself. It calls
    runPluginCommand with the URL and takes the program's stdout as the
    buffer (src/http.c:851-882). %i is the URL. %o would name an output
    file; without it the output is piped. %p prompts for a parameter.

  - outtype = h means "the output is html, carry on and browse it";
    outtype = t means text; no outtype means the plugin is a player and
    consumes the data itself (users guide, Plugin Descriptors).

  - Cookies that edbrowse would have sent are exported in the environment
    variable PLUGINHEADERS. We will not need them: our browser has its own
    cookie jar, which is the entire point.

  - Plugins can be turned off globally with pg-, or for one command with g-.

  - .ebrc can define functions invoked as <name, and the chrome plugin uses
    that to build commands out of the A command's output. That trick is
    worth stealing verbatim; see section 6.

So a `tweb://` protocol plugin gets us: `b tweb://https://site` starts a
session and the buffer fills with our html. That much is a fifteen-line
shell or node script.


3. The wall: forms cannot submit to a custom protocol
------------------------------------------------------

src/html.c:3081-3095, in infPush(), the code path taken when you press a
submit button with i*:

    if (post_string) {
        if (stringEqualCI(prot, "mailto")) { ... }
        else if (stringEqualCI(prot, "http") || stringEqualCI(prot, "gopher")) { ... }
        else if (!stringEqualCI(prot, "https") && !stringEqualCI(prot, "gophers")) {
            setError(MSG_SubmitProtBad, prot);
            goto fail;
        }
    }

MSG_SubmitProtBad is "cannot submit using protocol %s" (lang/msg-en). The
check applies to get and post alike — it is on the protocol of the action,
before the method is consulted.

Note also that runPluginCommand is only ever handed a URL (src/http.c:864).
There is no channel for a request body. Even if the protocol check were
relaxed, a POST to a plugin would arrive with its body dropped.

This kills the pure-plugin design for anything interactive. A search box, a
login, a comment field, a select — none of them can be submitted. Since half
the reason to drive a real browser is that we can log in and stay logged in,
that is not a limitation to accept.


4. The shape that works: a loopback HTTP origin
------------------------------------------------

tweb listens on 127.0.0.1 on an ephemeral port and serves the live tabs as
ordinary web pages. edbrowse talks http to it exactly as it would to any
site. Nothing about a custom protocol is needed for the session itself, and
everything edbrowse can do to a web page it can now do to ours.

Local port exposure is already an explicit non-issue for this project:
anything that can reach a new listener here can already reach the browser's
own debugging port and drive the browser directly. Bind to 127.0.0.1 anyway,
and put a random per-session token in the path (section 5) so that a stray
process cannot enumerate tabs by guessing URLs.

The plugin still earns its place as the entry point, because typing
`b http://127.0.0.1:41xxx/...` is nobody's idea of a URL bar:

    plugin {
        type = */*
        desc = Read a page through tweb's browser
        protocol = tweb
        program = edbrowse-plugin-tweb %i
        outtype = h
    }

`b tweb://https://skt222.bandcamp.com/album/weird-fish` runs the plugin; the
plugin asks the running tweb (or starts one) to open that URL in a tab and
prints the rendered document; that document begins with

    <base href="http://127.0.0.1:41xxx/t/<token>/3/">

and edbrowse resolves every relative link and every form action against it
(src/html-tags.c:1541 sets cf->hbase from <base>, and src/html.c:3054 uses
hbase as the default form action). From the second page onward the buffer is
a plain http URL and the plugin is out of the loop.

Section 12 weighs this against patching edbrowse instead, which is a real
option and a smaller patch than it sounds.

One consequence to design for deliberately. After the first navigation the
buffer's filename is our http URL, and rf re-reads that URL
(src/buffers.c:5437-5466: rf turns into `b <same url>` with nostack). If an
element-activation URL is the thing being re-read, rf would click the button
again. Use the post/redirect/get pattern: activation URLs answer 302 to the
tab's idempotent view URL, edbrowse follows the redirect and adopts the final
URL as the filename (src/http.c:3332, changeFileName). Then rf always means
"render this tab as it is now", which is exactly the refresh semantics we
want, and it is the closest thing edbrowse has to our live updating.

Serve `Cache-Control: no-cache` (src/http.c:210-223 honours no-cache in
Cache-Control or Pragma), or rf will sometimes hand back the previous render.


5. Tab-element ids
------------------

The id space is the heart of it. Proposed URL shapes, all under a per-session
token so the paths are unguessable:

    /t/<token>/<tab>/                  the tab, rendered (idempotent)
    /t/<token>/<tab>/ax                the accessibility view
    /t/<token>/<tab>/text              the visible-text view
    /t/<token>/<tab>/source            the markup, as tweb's SOURCE view
    /t/<token>/<tab>/e<id>             activate element (302 back to the tab)
    /t/<token>/<tab>/e<id>/click       activate with a real, trusted click
    /t/<token>/<tab>/e<id>/media       proxy the element's media bytes
    /t/<token>/<tab>/submit/e<id>      form submit, fields named e<id>
    /t/<token>/<tab>/close             close the tab
    /t/<token>/tabs                    the tab list

The id itself: `<generation>.<index>`, where generation is bumped on every
render of that tab and index is the position in the array of activatable
elements found by that render. tweb keeps, per tab, a map from id to a live
element handle — the same handles the reader already holds. This is better
than a DOM path or a selector because it survives the page mutating around
the element, and it costs nothing: we already register every element we
describe.

Staleness is the interesting case, and it is not hypothetical: the buffer in
edbrowse is a snapshot, the page moves on, and the reader activates a link
from a render three generations old. Three-tier answer, all of which tweb
already has the machinery for:

  1. If the handle is still attached to the document, use it. Nothing else
     matters — the element is the element.
  2. If it is detached, re-resolve by the same evidence place.js uses across
     views: the accessible name, the tag, and the element's position in
     document order (describeElement/locateElement). If exactly one candidate
     matches well, use it and say so in the response.
  3. Otherwise answer 409 with a one-line page saying the element is gone and
     the page has changed, and let the reader type rf. Never guess.

Generations also give a cheap staleness signal: if the reader activates an
id from generation 4 while the tab is at generation 9, we know to re-check
before acting rather than after.

Which elements get an id: everything tweb's HTML view already considers
notable (a, button, input, select, textarea, summary, details, and friends),
plus anything carrying an interactive ARIA role, plus anything with
tabindex, plus — the useful heuristic — anything whose computed cursor is
`pointer`. That last one catches the div-with-a-click-handler that has been
the recurring problem on real pages; the Bandcamp play button is exactly
that shape (an <a role=button> whose handler lives on the <div> inside it).

Chromium could do better than heuristics via DOMDebugger.getEventListeners,
which really does enumerate listeners; Firefox over BiDi has no equivalent.
Since the two engines must describe the same page, the heuristic set is the
honest common denominator, and the /click URL covers whatever it misses.


6. Mapping each interaction
---------------------------

Links. Rendered as ordinary anchors pointing at /e<id>. edbrowse shows them
as {text} and g follows them. Nothing to invent.

Real clicks. tweb distinguishes activation through the DOM's default action
(Enter) from a trusted click carrying user activation (m), and the
distinction matters on real pages — audio will not play without it. In
edbrowse there is no second key to press, so it becomes a second URL,
/e<id>/click, and a function in .ebrc that rewrites the link on the current
line. This is precisely what the chrome plugin does with the A command, so
the idiom is established:

    function+twebclick {
        db0
        A
        2,d
        s;^<br/*><a href='\(.*\)'>$;b $1/click;f
        bw
        up
        js-
        db1
        <*-1
    }

Line by line, and this is render-chrome.rc's own shape: A pushes a scratch
session holding `<br><a href='URL'>` for each link on the line (users guide,
Web And Email Addresses); 2,d keeps the first; the substitution rewrites it
into the edbrowse command `b <url>/click`, with the f flag so the reader's
own search and substitute strings are left alone; bw marks the scratch buffer
written so it can be discarded; up returns to the page; <*-1 runs the command
sitting one buffer down in the history, stopping on error. The reader types
<twebclick on the line holding the play button.

The same construction, with a different substitution, gives the other two
things worth binding: <twebrf for refresh-in-place (section 7) and a "what is
this line" that prints the element id, though g? already prints the URL.

Buttons that are not submit buttons. edbrowse presses these with i*, which
runs their javascript — and we will be running with js off, because our
browser has already run the page's scripts and edbrowse must not run them
again. So do not render them as <button>. Render every non-form control as a
link to /e<id>. It costs nothing in readability: edbrowse shows {Play Weird
Fish} either way, and g works.

Forms. Render as real forms, with the action pointing at
/submit/e<submit-button-id> and every field named after its own element id:

    <form action="submit/e9.31" method="post">
    <input name="e9.28" value="">
    <select name="e9.29"> ... </select>
    <input type="submit" name="e9.31" value="Search">
    </form>

edbrowse then does what it is good at: i? describes the field, i= sets it,
i?string filters a long select, ib gives a textarea its own editing session,
ipass hides a password, i* presses the button. On submit we receive a body
of id=value pairs with no ambiguity about which control each belongs to.

What tweb does with that body, in order: set each field's value on the live
element, dispatch input and change events so the site's own handlers and
validation run, then activate the submit button with a *trusted* click. The
values are set programmatically rather than typed, which is fast and right
for ordinary fields; the submit is a real click, which is what earns user
activation for whatever the submission sets off. Where a site genuinely
demands per-keystroke behaviour (an autocomplete that only fires on keydown),
the fallback is to focus the field and type it through the browser's input
pipeline, as tweb's typing mode already does — slower, so make it the
exception, chosen per element rather than globally.

Method: use post. GET would put the values in the URL, which then becomes the
buffer's filename, which rf would replay — and replaying a submission is the
one thing we are trying to avoid. Post, then 302 to the tab view.

Text areas. Render as <textarea>; edbrowse's ib/if machinery is nicer than
anything we would build. The value arrives in the post body like any other
field.

File uploads. Not supported, and probably never: the browser will not accept
a path from us for a file input, and edbrowse has no notion of attaching one
to a form. Render the control as text saying so.

Frames. tweb already inlines child frames where they sit, including
cross-origin ones the page-side script could never reach. Keep doing that and
do not emit <iframe>, or edbrowse will show a {frame} link and try to fetch
the real site itself — without the browser's session, which is the whole
advantage.

Media and downloads. An <audio> or a link to an .mp3 is where edbrowse's own
plugins shine: mpv or mpg123 will play it if edbrowse can fetch it. But the
bytes usually need the browser's cookies. Serve /e<id>/media as a proxy that
streams what the browser would have fetched, so edbrowse's media plugins get
an authenticated stream from a plain http URL. Range requests matter here if
seeking is to work.

Images. Alt text, as edbrowse already renders [alt text]; nothing to do.

Tabs. /tabs is a page of links, one per open tab, plus a close link each.
Shift+F4 in the reader becomes "g on the close link", and edbrowse's own
sessions (e1, e2, …) can hold different tabs if the reader wants them side
by side. Do not try to drive edbrowse's session numbers from our side; there
is no channel for it.

The four views. /ax, /text, /source alongside the default render. Backslash
becomes "browse a different URL", which loses the keep-your-place behaviour
that took real work to get right (place.js). Mitigation in section 7.


7. What does not map, and what to do about it
----------------------------------------------

Live updates. edbrowse has no way to be told anything. There is no channel
from a plugin or an http response to an idle buffer. Everything tweb does
with a MutationObserver, the freeze-while-you-read rule, the cheap text
patches, the "3 areas changed, press c" status — all of it evaporates. What
remains is rf, which is cheap and idempotent by design (section 4). This is
the single largest loss in the whole exercise and it is worth being clear
about it before starting.

Announcements. aria-live regions currently reach the reader immediately. In
edbrowse they can only be seen when something is rendered. Two partial
answers: pin any announcement that arrived since the last render to the top
of the next one (so rf shows it), and expose /tabN/announce as a page of the
recent ones for a reader who wants to check. Neither is immediate; nothing
can be.

Keeping your place across rf. rf builds a fresh window (src/buffers.c:5437,
noStack = 2) and the previous line number does not come with it. Since we
generate the html we can give every element an anchor id, and edbrowse jumps
to a #fragment when browsing a URL that has one. So a refresh-in-place
function is possible: capture the current line's element id with A, rewrite
it to the tab view plus #e<id>, and browse that. Same trick as <clickreal,
and it is the closest thing to tweb's re-anchoring available here.

The reading model. tweb's line list is one item per line with the terminal
cursor as the position, and its column-level movement reads straight through
a page. edbrowse's line is edbrowse's line: its own wrapping at ~80
characters at phrase boundaries, its own {link} and <field> notation, its own
table pipes. That is the trade being made deliberately — edbrowse's renderer
in exchange for tweb's — and it is a reasonable one, since edbrowse's
handling of tables, lists and forms is better than ours and its editor is far
better than our buffer.

Accessible names. Handing edbrowse the raw DOM loses everything the
accessibility tree knows. An icon-only control renders as {} — a link with no
text — and the page becomes unreadable in exactly the places tweb currently
reads best. So the document we generate must be enriched: where an element's
rendered text is empty and it has an accessible name, emit that name as the
element's text. This is the AX work paying for itself inside edbrowse's
renderer, and it is why "just hand over document.documentElement.outerHTML"
is not good enough.

Character-level position, quick-nav keys (h/l/f/b/n/p), the change list, the
view cycle and the freeze rules are all reader features that simply do not
exist on the other side. edbrowse has its own vocabulary for most of it —
searching, line numbers, the stack — and the reader will use that instead.


8. The document we generate
----------------------------

Rules, all of which we already have the pieces for:

  - Start from the live DOM (the same source SOURCE view reads), not the
    network response. The page has already run its scripts in a real browser;
    that state is the thing worth handing over.
  - Strip <script>, <style>, <link rel=stylesheet>, and every on* attribute.
    edbrowse must not run any of it: its javascript engine would be
    interpreting a page that has already run, in a DOM that is a copy, with
    no network identity. Recommend js- in the session as well.
  - Rewrite every href, action and src that we own into ids; leave external
    media URLs alone only if we do not need cookies for them.
  - Inline child frames in document order, as the reader already does.
  - Inject accessible names where the visible text is empty.
  - Emit an anchor id for every element that has an id, so #fragments work.
  - Keep the output stable across renders when the page has not changed: the
    same page must serialise the same way twice, or rf will look like churn.
  - Keep <table>, <ul>, <ol>, <dl>, <h1>-<h6>, <pre> exactly as they are.
    This is the whole reason for the exercise — edbrowse renders these well
    and tweb's line list flattens them.

Size is worth watching: SOURCE view of a Wikipedia article is ~17,000 lines,
and edbrowse will parse and hold whatever we send.


9. Failure modes to design for
-------------------------------

  - The page navigated under the reader between render and activation. Detect
    via the generation, re-render, and answer 409 with an explanation rather
    than clicking something arbitrary.
  - A real click is refused because something covers the element (a cookie
    dialog, a modal). tweb already detects this precisely and names the
    covering element; return that text as the page rather than a silent
    failure. Since the dialog is in the document we serve, the reader can go
    and dismiss it — which is exactly what the shadow-DOM work made possible.
  - Activation takes too long. Everything in tweb is already bounded at six
    seconds; the http response must be bounded too, and must say what it was
    waiting for.
  - The browser is not running. The plugin should start one, the same way the
    reader does, and say so.
  - Two edbrowse sessions on one tab. tweb already claims tabs per reader
    (session.js); the same claim logic applies to edbrowse sessions, and the
    tabs page should show which are claimed.
  - Never, under any pressure, fall back to a headless or automation-launched
    browser to make any of this easier. That is the one rule the whole
    project rests on.


10. What to build first
------------------------

Smallest useful thing, in order. Each step is usable on its own.

  1. The http server with /t/<token>/<tab>/ and the document generator, no
     ids, no activation. Read-only pages from the live browser, rendered by
     edbrowse. This alone is already better than the chrome plugin: a real
     browser's post-javascript DOM, logged in, no bot checks.
  2. The entry-point plugin and <base href>, so `b tweb://url` works and
     relative links resolve. Still read-only.
  3. Ids and /e<id> activation with the 302-back-to-view pattern. Links and
     buttons now work, and rf is safe.
  4. Forms: /submit/e<id>, value-setting, events, trusted click on submit.
     This is the step that makes it a browser rather than a viewer.
  5. /e<id>/click plus the .ebrc functions for the real click and for
     refresh-in-place with a fragment.
  6. The extra views, the tabs page, the media proxy.

Stopping after 3 leaves something genuinely usable for reading the web in
edbrowse. Stopping after 4 leaves something that can log in and search.


11. Decisions I cannot make for you
------------------------------------

  - Does the edbrowse path replace the tweb reader, or live beside it? They
    can share everything below the terminal layer, but the freeze/announce
    policy and place-keeping only pay off in the reader, and maintaining both
    means maintaining two answers to "where is the user".
  - One tab per edbrowse session, or one session driving many tabs through
    the tabs page? The first is more natural in edbrowse and needs no state;
    the second matches how tweb thinks today.
  - How much of the AX view's judgement should leak into the html: only names
    where text is missing (conservative, recommended), or roles and states as
    well, which would mean generating markup that is not what the page says.
  - Whether the media proxy is worth it, or whether handing edbrowse the raw
    media URL and accepting the occasional 403 is good enough.


12. Transport: three shapes, and why this one
----------------------------------------------

The obvious objection to a loopback server is that it adds a layer. It does
not, and counting the processes is the quickest way to see why.

  A. loopback http     edbrowse -> tweb -> browser
  B. plugin protocol   edbrowse -> fork a plugin per fetch -> tweb -> browser
  C. stateless plugin  edbrowse -> fork a plugin per fetch -> browser

The plugin in B is not a layer you avoid: edbrowse forks it for every fetch,
and it has to reach something that holds the browser session, so B is A plus
a fork per click plus an IPC of our own devising. A is the smaller topology,
addressed with a protocol both ends already speak, and testable with curl.

C is the one that genuinely removes a layer, and it is not silly. It needs
ids that resolve without any stored state, so a short-lived process can
attach to the running browser, resolve, click, re-render and exit. tweb
rejoins a running browser in 35ms (Firefox) or 50ms (Chromium), and a
snapshot is 150-500ms, so a click would cost around a second. Two things make
it awkward rather than impossible: Firefox serves one WebDriver session at a
time, so a per-click process fights any running reader, and there is no http
status line, so the redirect that keeps rf idempotent has to become a <meta
http-equiv=refresh> in the returned document (edbrowse honours those,
src/buffers.c:9035).

Patching edbrowse for B is smaller than section 3 implies. The protocol check
in infPush is the only gate, and the form data is already there when the
plugin is dispatched: http.c:853 runs the plugin before http.c:947 splits the
post body off, and urlSanitize is called there with no post pointer, so %i
carries the whole string — ?data for get, \1data for post. Allowing a
protocol that has a plugin registered is a three-line change. It is in
patches/edbrowse-submit-to-plugin-protocols.patch, along with
patches/edbrowse-rf-keeps-your-place.patch, which gives rf the same treatment
f_dot already gives ub and b. Both are worth sending upstream on their own
merits; neither is needed by anything here.

So: build A, because it needs no patched edbrowse and works for anyone with a
stock one, and it gets the 302 and the media proxy for free. Keep the two
patches anyway, because they are cheap and general.

What actually locks us in is not the transport but the id scheme. Ids here
are structurally derived and registry-cached: an id names a descriptor — a
path through the document (crossing shadow roots), the tag, the accessible
name and the position in document order — and that descriptor can be resolved
by any process with a connection to the browser, with no shared memory and no
handle table. The registry only remembers which descriptor got which number,
so the same element keeps the same id across renders and a link in a stale
buffer still means something.

That choice keeps all three shapes open. Moving from A to B or C later is a
change of transport, not a redesign: the document generator and the id scheme
are the durable work, and they do not know how the bytes get to edbrowse.


13. What is built, and what is not
-----------------------------------

Built, and exercised against a real browser with curl driving it the way
edbrowse will (npm run edb, src/edb_server.js, src/edb_page.js):

  - tabs list, render, close; the ax, text and source views as <pre>.
  - ids as descriptors, resolved in the page, stable across renders.
  - activation, and a real trusted click on /click.
  - forms: values set on the live elements, input and change dispatched, the
    submit pressed as a person would press it. Bandcamp's search lands on
    "Search: ambient | Bandcamp".
  - loose fields — no form around them — wrapped in one of their own, whose
    button focuses the field and presses Enter in the page.
  - 302 back to the tab after every action, and no-cache on everything, so rf
    is a refresh rather than a repeat.
  - the entry-point plugin and its config fragment (edbrowse-plugin/).
  - an address field on line 1 of every page served, the four shortcuts, and
    addresses taken the way a url bar takes them (section 14).
  - noticing that the browser has closed and starting another, rather than
    answering every later request with Playwright's words for it.

Not built yet, in the order they are likely to be wanted:

  - The media proxy (/e<id>/media). Media links currently point wherever the
    page points, so a stream that needs the browser's cookies will 403 in
    edbrowse's mpv plugin.
  - Frames render by position (the Nth frame element is the Nth child
    context, the same assumption the reader has always made) and only one
    level deep. Nested frames are not reachable.
  - Announcements. Nothing collects aria-live regions for the next render,
    so anything the page says while you are reading is lost.
  - Stale-id recovery is implemented but has not been exercised against a
    page that really did change underneath a buffer; the third tier (409 and
    "type rf") has never been seen.
  - Text areas are emitted as <textarea> and edbrowse's ib should work, but
    that path has not been tried.
  - Nothing claims tabs the way the reader does, so a reader and an edbrowse
    session can both be pointed at the same tab and will fight.


14. Getting in: what the reader has to remember
------------------------------------------------

`b tweb://https://example.com` is three things to remember — a command, a
protocol nobody outside this project has heard of, and a scheme the reader
was not thinking about — and forgetting any of them is an error message. The
answers, in the order a reader meets them:

  - The scheme is the server's problem. /open now takes an address the way a
    url bar takes one: a host with a dot gets https, localhost and the
    loopback addresses get http, and something with no host in it is not an
    address — say so and offer a search, rather than quietly sending what was
    typed to a search engine. This is one implementation, in the server,
    because the plugin and the address field both arrive there.

  - The command and the protocol are shortened by .ebrc functions, which take
    arguments (~0 is the whole of what was typed after the name; the users
    guide builds a duckduckgo shortcut this way). `<t address`, `<tt` for the
    tab list, `<ts words` to search. Two lines each, renamable.

  - Neither is needed once you are in, because line 1 of every page tweb
    serves is an address field. This is the part that cannot be forgotten: it
    is in the buffer, where the reader already is. It works because edbrowse
    numbers input fields within the current line (users guide, `i=xyz : set
    the input field on the current line`), so a line holding exactly one field
    and one button is `i=address` then `i*` with nothing to count.

    The four views and the tab list carry it too, since those are exactly the
    pages you are on when you want to go somewhere else. They also carry a
    <base>, because `b tweb://tabs` leaves the buffer's filename a tweb:// url
    that no relative link would resolve against.

What was considered and not done: making tweb the transport for *all* of
edbrowse's browsing, so that plain `b example.com` goes through the browser.
edbrowse would allow it — a plugin can match on `urlmatch`, which is a
case-insensitive substring test against the url (isup.c:3054 findMimeByURL),
so `urlmatch = http://|https://` matches every page. The problem is that it
also matches the pages tweb itself serves, since those are http on loopback,
and urlmatch has no negation: every link in a tweb page would re-enter the
plugin, forever.

There are two ways out and both are real work. The plugin could proxy: notice
its own origin and simply fetch it, which costs a fork per click and loses the
status line, so the 302 that keeps rf idempotent would have to become a <meta
http-equiv=refresh> in the body (edbrowse honours those, buffers.c:9035).
Or edbrowse could learn an exclusion — a `urlnomatch` beside `urlmatch` — which
is a smaller patch than it sounds and would belong in patches/ with the other
two. Neither is needed by anything above, and the first changes every fetch
edbrowse makes, which is a decision about what edbrowse is for rather than a
convenience.


15. When the browser goes away
-------------------------------

The reader closes the browser. Nothing in this design survives that on its
own: every page object in the server names a target that no longer exists,
and Playwright answers each request with "browserContext.newPage: Target
page, context or browser has been closed" — a sentence naming no cause and
suggesting no action — for the rest of the session.

So the server asks first. Each driver can say whether its browser is still
there (isConnected over CDP; the socket's state over BiDi), the server checks
before it touches one, and if the answer is no it starts one the same way the
session started the first: ordinary, rejoined or spawned, never automated.
That rule does not bend for convenience here either.

Tab numbers are the interesting part, because they are in the reader's buffer
and in edbrowse's stack, and they now name nothing. Tabs carries the urls
over the restart, so a number that has lost its page is answered with the
address it last held and a link to open it again — one `g` from where the
reader already is — rather than with the news that a number is meaningless.
The same page serves a tab the reader closed themselves.

What is deliberately not done: watching for the browser's exit and restarting
it eagerly. A reader who closes the browser has closed it; the right moment
to start another is when they next ask for a page.
